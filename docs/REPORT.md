## ۱. معرفی پروژه

### ۱.۱. دامنه مسئله

در شهر قم، مجموعه‌های ورزشی متعدد (فوتسال، والیبال، بسکتبال، هندبال، فوتبال) فعال هستند، اما فرآیند رزرو زمین به صورت سنتی (تماس تلفنی، مراجعه حضوری) انجام می‌شود. این روش مشکلات زیر را به همراه دارد:

- **عدم شفافیت:** کاربر از وضعیت خالی یا پر بودن زمین مطلع نیست.
- **دوبار رزرو شدن:** احتمال رزرو همزمان یک سانس توسط دو نفر.
- **عدم مدیریت مالی:** محاسبه دستی درآمد، جریمه‌ها و تسویه‌حساب.
- **عدم دسترسی به تاریخچه:** کاربر و مدیر سابقه رزروهای خود را ندارند.

### ۱.۲. هدف سیستم

توپ‌سِت یک پلتفرم تحت وب برای **کشف، رزرو و پرداخت آنلاین زمین‌های ورزشی** با اولویت تجربه کاربری فارسی‌زبان (RTL، گاهشماری جلالی، اعداد فارسی) است.

### ۱.۳. ذی‌نفعان (Stakeholders)

| ذی‌نفع                    | نقش                                            |
| ------------------------- | ---------------------------------------------- |
| **کاربر عادی**            | جستجو، مشاهده، رزرو، پرداخت، لغو، ثبت نظر      |
| **مدیر مجموعه (Manager)** | مدیریت سانس‌ها، تأیید رزرو دستی، درخواست تسویه |
| **مدیر سیستم (Admin)**    | مدیریت کاربران، مجموعه‌ها، تنظیمات، گزارش‌ها   |
| **توسعه‌دهنده**           | نگهداری کد، استقرار، مانیتورینگ                |

## ۳. معماری سیستم

### ۳.۱. معماری کلی (لایه‌ای - Layered Architecture)

```
┌─────────────────────────────────────────────────────┐
│                   کلاینت (Next.js 16)                │
│          Persian-first UX, RTL, Dark Mode            │
├─────────────────────────────────────────────────────┤
│                   API Routes (/api/v1/*)             │
│                Dependency Injection (4-level Auth)    │
├─────────────────────────────────────────────────────┤
│            سرویس‌ها (Services/*)                      │
│         منطق کسب و کار، اعتبارسنجی، هماهنگی           │
├─────────────────────────────────────────────────────┤
│           مخازن (Repositories/*)                     │
│          CRUD ناهمگام با SQLAlchemy 2.0              │
├──────────────────┬──────────────────────────────────┤
│   PostgreSQL 17   │            Redis 7               │
│  ایندکس‌گذاری کامل  │   حافظه‌گذاری، محدودیت نرخ،    │
│  connection pool  │       نشست‌های کاربران            │
└──────────────────┴──────────────────────────────────┘
```

| لایه               | فناوری                                                                       |
| ------------------ | ---------------------------------------------------------------------------- |
| **Frontend**       | Next.js 16 + React 19 + TypeScript + Tailwind v4 + shadcn/ui (radix-nova)    |
| **Backend**        | Python 3.12+ / FastAPI / SQLAlchemy 2.0 (async) / Alembic                    |
| **Database**       | PostgreSQL 17 + asyncpg                                                      |
| **Cache/Session**  | Redis 7                                                                      |
| **Authentication** | JWT (HS256, kid header, dual-key rotation) + bcrypt + refresh token rotation |

| **Localization**   | Persian (fa-IR): RTL, Jalali dates, Persian digits                           |
| **Monitoring**     | Prometheus + Grafana + OpenTelemetry + Sentry                                |
| **Container**      | Docker Compose (multi-stage builds, healthchecks)                            |
| **CI/CD**          | GitHub Actions (lint, test, build, publish to ghcr.io)                       |

### ۳.۳. میان‌افزارها (Middleware Stack)

ترتیب اجرای میان‌افزارها در FastAPI:

1. **CORSMiddleware** — مدیریت Cross-Origin Requests
2. **CorrelationIdMiddleware** — انتشار X-Request-ID در تمام سرویس‌ها
3. **ProfilerMiddleware** — زمان‌سنجی تفکیکی هر درخواست (DB, Redis)
4. **SecurityHeadersMiddleware** — هدرهای امنیتی OWASP (CSP, HSTS, XFO, ...)
5. **PrometheusMiddleware** — متریک‌های HTTP (تعداد، تأخیر)
6. **SlowAPIMiddleware** — محدودیت نرخ مبتنی بر Redis

### ۳.۴. وظایف پس‌زمینه (Background Tasks)

دو تسک asyncio در طول عمر (lifespan) برنامه اجرا می‌شوند:

- **Metrics Refresh** — هر ۱۲۰ ثانیه: به‌روزرسانی business gauges (تعداد کاربران، مجموعه‌ها، درآمد، رزروها)
- **Expired Booking Cleanup** — هر ۶۰ ثانیه: لغو رزروهایی که مهلت ۱۰ دقیقه‌ای پرداخت آن‌ها منقضی شده، آزادسازی سانس‌ها

## ۵. لایه‌های نرم‌افزار

### ۵.۱. معماری لایه‌ای (N-Tier)

**الف. لایه مسیریابی (Routes) — `backend/app/api/v1/*.py`**

۱۸ روتر نازک (Thin Router) که هیچ منطق کسب و کاری ندارند. فقط:

- دریافت درخواست HTTP
- تزریق وابستگی‌ها (Auth Dependencies)
- فراخوانی سرویس‌ها
- بازگشت پاسخ

**ب. لایه سرویس (Services) — `backend/app/services/*.py`**

۱۳ سرویس اصلی که منطق کسب و کار را پیاده‌سازی می‌کنند:

| سرویس                | مسئولیت                                                     |
| -------------------- | ----------------------------------------------------------- |
| `AuthService`        | ثبت‌نام، ورود رمزعبور، ورود OTP، خروج، مدیریت نشست          |
| `OTPService`         | ارسال کد تأیید (شبیه‌سازی‌شده)                              |
| `BookingService`     | رزرو، پرداخت، لغو، محاسبه جریمه، جایگزینی                   |
| `FinanceService`     | استرداد وجه، ثبت کارت بانکی، درخواست تسویه، مدیریت جریمه‌ها |
| `PaymentService`     | شبیه‌سازی درگاه پرداخت (موفق، مردود، تقلب)                  |
| `VendorService`      | CRUD مجموعه‌ها، مدیریت تصاویر، مدیریت سانس‌ها               |
| `TimeSlotService`    | تولید خودکار سانس‌ها از برنامه هفتگی                        |
| `DashboardService`   | آمار و گزارش‌های داشبورد (کاربر/مدیر/ادمین)                 |
| `ReviewService`      | ثبت و مدیریت نظرات                                          |
| `ReplacementService` | جایگزینی رزرو (تعویض سانس)                                  |
| `FavoriteService`    | مدیریت علاقه‌مندی‌ها                                        |
| `BankCardService`    | افزودن/تأیید کارت بانکی                                     |
| `CacheService`       | حافظه‌گذاری Redis                                           |
| `UserService`        | مدیریت کاربران (ادمین)                                      |

**ج. لایه مخازن (Repositories) — `backend/app/repositories/*.py`**

۱۵ مخزن که CRUD ناهمگام با SQLAlchemy 2.0 را پیاده‌سازی می‌کنند:

- **یک کلاس به ازای هر مدل**
- عدم دسترسی مستقیم سرویس‌ها به نشست دیتابیس — فقط از طریق مخازن
- استفاده از `selectinload` برای بارگذاری روابط

**د. لایه مدل‌ها (Models) — `backend/app/models/*.py`**

تعریف موجودیت‌ها با SQLAlchemy ORM و Type-Annotated Mapped Columns.

**ه. لایه اعتبارسنجی (Schemas) — `backend/app/schemas/*.py`**

۲۰ مجموعه Pydantic v2 مدل برای:

- درخواست‌های ورودی (Request Schemas)
- پاسخ‌های خروجی (Response Schemas)
- خطاها (Error Schemas)

## ۶. احراز هویت و امنیت

### ۶.۲. JWT با چرخش کلید

- **الگوریتم:** HS256
- **هدر:** شامل `kid: "v1"` برای پشتیبانی از چرخش هم‌زمان دو کلید
- **Access Token:** ۳۰ دقیقه اعتبار
- **Refresh Token:** ۷ روز اعتبار (کوکی HTTP-only)
- **چرخش توکن رفرش:** هر بار استفاده، توکن جدید صادر و توکن قبلی باطل می‌شود
- **شناسایی چرخش اجباری:** در صورت تلاش برای استفاده از توکن باطل‌شده، تمام نشست‌های کاربر بی‌اعتبار می‌شود

### ۶.۳. امکانات امنیتی دیگر

- **Token Versioning:** افزایش `token_version` کاربر باعث باطل شدن تمام توکن‌های قبلی می‌شود
- **محدودیت نرخ:** Redis-backed با fallback درون حافظه‌ای
- **هدرهای امنیتی OWASP:** CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Permissions-Policy, Referrer-Policy
- **پالایش آپلود:** تشخیص MIME با magic bytes، حذف XSS از SVGهای آپلودی
- **کرنومتر:** ۳۲ کاراکتر حداقل طول `SECRET_KEY`
- **اعتبارسنجی محیط اجرا:** بررسی کامل متغیرهای محیطی در startup

## ۷. گردش کار فرآیندهای اصلی

### ۷.۱. فرآیند رزرو (Core Use Case)

```
1. کاربر مجموعه را جستجو و انتخاب می‌کند
2. سانس مورد نظر را در نمای ۷ روزه انتخاب می‌کند
3. در صورت نیاز، توپ را انتخاب می‌کند
4. --- Lock خوش‌بینانه (Optimistic Locking) ---
5. سیستم قیمت را محاسبه و به کاربر نمایش می‌دهد
6. رزرو با وضعیت PENDING_PAYMENT ایجاد می‌شود
7. تایمر ۱۰ دقیقه‌ای برای پرداخت شروع می‌شود
   │
   ├── کاربر پرداخت می‌کند:
   │     └── status → CONFIRMED ✅
   │
   ├── تایمر منقضی می‌شود:
   │     └── تسک پس‌زمینه status → EXPIRED ❌
   │     └── سانس آزاد می‌شود
   │
   └── کاربر لغو می‌کند:
         └── < ۲ ساعت قبل: غیرممکن 🚫
         └── ۲-۲۴ ساعت قبل: جریمه ۵۰٪، مابقی به کیف پول 💰
         └── > ۲۴ ساعت قبل: استرداد کامل به کیف پول ✅
```

### ۷.۲. فرآیند احراز هویت (OTP)

```
کاربر شماره تلفن را وارد می‌کند
  │
  ├── شماره جدید است → ثبت‌نام
  │     └── OTP ارسال می‌شود (شبیه‌سازی در کنسول)
  │     └── کاربر کد را وارد می‌کند → JWT صادر می‌شود
  │
  └── شماره موجود است → ورود
        └── OTP ارسال می‌شود
        └── کاربر کد را وارد می‌کند → JWT صادر می‌شود

نکته: پس از ۵ تلاش ناموفق OTP، کاربر ۳۰ دقیقه قفل می‌شود.
```

### ۷.۳. فرآیند تسویه حساب

```
مدیر مجموعه درخواست تسویه می‌دهد
  │
  └── ادمین درخواست را بررسی می‌کند
        ├── تأیید ناقص → درخواست پاسخ داده می‌شود
        ├── تأیید → مبلغ تصویب شده
        │     └── پرداخت انجام می‌شود → وضعیت PAID
        │           └── رزروهای مرتبط: status → SETTLED
        └── رد → رزروها آزاد می‌شوند
```

### ۷.۴. فرآیند لغو و جایگزینی

```
رزرو تأیید شده
  │
  ├── لغو توسط کاربر (در بازه مجاز):
  │     └── Booking → PENDING_CANCELLATION
  │     └── TimeSlot → PENDING_CANCELLATION (رزرو شده برای جایگزینی)
  │     └── کاربر جدید می‌تواند این سانس را بگیرد
  │     └── پس از رزرو جدید → رزرو قبلی CANCELLED و استرداد انجام می‌شود
  │
  └── لغو توسط مدیر مجموعه:
        └── استرداد کامل (نوع MANAGER_CANCELLATION)
```

### ۱۰.۳. انطباق با اصول SOLID

| اصل                           | وضعیت | شواهد                                                       |
| ----------------------------- | ----- | ----------------------------------------------------------- |
| **S** — Single Responsibility | ✅    | هر سرویس یک مسئولیت مشخص دارد (Booking, Finance, Auth, ...) |
| **O** — Open/Closed           | ✅    | مخازن و سرویس‌ها برای توسعه باز، برای تغییر بسته            |
| **L** — Liskov Substitution   | ✅    | Dependency Injection با Interfaceهای ضمنی (Protocol-based)  |
| **I** — Interface Segregation | ✅    | دیپ‌های احراز هویت مجزا (۴ سطح)                             |
| **D** — Dependency Injection  | ✅    | تزریق وابستگی در سازنده سرویس‌ها و روترها                   |

### ۱۰.۴. انطباق با الگوهای معماری

| الگو                           | سطح     | توضیح                                                 |
| ------------------------------ | ------- | ----------------------------------------------------- |
| **Repository Pattern**         | ✅ کامل | جدا کردن کامل دسترسی به داده از منطق کسب و کار        |
| **Service Layer**              | ✅ کامل | منطق کسب و کار در سرویس‌ها، نه در روترها              |
| **Dependency Injection**       | ✅ کامل | استفاده از FastAPI Depends برای تزریق                 |
| **DTO (Data Transfer Object)** | ✅ کامل | Pydantic schemas برای اعتبارسنجی و تبدیل              |
| **Unit of Work**               | ✅ نسبی | مدیریت session در`get_db()` با commit/rollback خودکار |
| **Strategy**                   | ✅ نسبی | PaymentService/SMSProvider با حالت mock               |

| **Singleton**                  | ✅ کامل | Redis client, Settings                                |
