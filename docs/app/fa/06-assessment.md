# بخش ۵ — ارزیابی کدبیس

## کیفیت معماری

**امتیاز: قوی (۸/۱۰)**

معماری ۳ لایه (API → سرویس → ریپازیتوری) به طور مداوم در تمام دامنه‌ها اعمال شده است. جداسازی وظایف تمیز است: ریپازیتوری‌ها دسترسی به داده را مدیریت می‌کنند، سرویس‌ها منطق کسب‌وکار را مدیریت می‌کنند، هندلرهای API مسائل HTTP را مدیریت می‌کنند. استفاده از تزریق وابستگی FastAPI برای احراز هویت و نشست‌های DB اصیل و قابل تست است.

**نقاط قوت:**
- لایه‌بندی مداوم در بیش از ۱۵ دامنه
- الگوی ریپازیتوری پیچیدگی کوئری را از منطق کسب‌وکار جدا می‌کند
- اسکیماهای Pydantic قراردادهای API واضح را اعمال می‌کنند
- وظایف پس‌زمینه (پاکسازی رزروهای منقضی، به‌روزرسانی متریک‌ها) از طریق lifespan به طور تمیز یکپارچه شده‌اند

**نقاط ضعف:**
- سرویس‌ها مستقیماً `HTTPException` را raise می‌کنند (لایه سرویس را به مسائل HTTP کوپل می‌کند)
- برخی سرویس‌ها بسیار بزرگ هستند (booking_service.py ~۸۰۰ خط) — می‌توانند به زیرسرویس‌ها تقسیم شوند
- کلاس‌های پایه انتزاعی/اینترفیس برای ریپازیتوری‌ها وجود ندارد — تعویض پیاده‌سازی نیاز به تغییر import دارد

---

## کیفیت بک‌اند

**امتیاز: قوی (۸/۱۰)**

بک‌اند Python با ساختار خوب، خوب تست شده با الگوهای ناهمزمان مدرن.

**نقاط قوت:**
- ناهمزمان در سراسر کد (asyncpg، SQLAlchemy ناهمزمان، aioredis)
- پول اتصال با pre_ping و تنظیمات پیش‌فرض مناسب تنظیم شده
- زمان‌سنجی کوئری در لایه دیتابیس تعبیه شده
- اعتبارسنجی جامع محیط در زمان راه‌اندازی
- تخریب تدریجی در صورت خرابی Redis (cache miss، fallback محدودکننده نرخ)

**نقاط ضعف:**
- `PaymentService` و `SmsProvider` mock هستند و الگوی آداپتر برای پیاده‌سازی واقعی ندارند
- برخی ریسک‌های N+1 با lazy-loading پیش‌فرض (بدون `selectinload` صریح در تعاریف مدل)
- مدیریت خطای وظایف پس‌زمینه ابتدایی است (catch-all + حلقه sleep)

## کیفیت دیتابیس

**امتیاز: بسیار قوی (۹/۱۰)**

اسکیما به خوبی نرمال شده، به درستی ایندکس شده و از ویژگی‌های PostgreSQL به طور مؤثر استفاده می‌کند.

**نقاط قوت:**
- ایندکس partial unique (`uq_bookings_one_active_per_slot`) ظریف و صحیح است
- قفل خوش‌بینانه از طریق فیلد version — محافظت مناسب از رزرو همزمان
- استفاده مداوم از TIMESTAMPTZ (بعد از مایگریشن `0009`)
- ایندکس‌های FK جامع (به صورت گذشته‌نگر از طریق مایگریشن‌های اختصاصی کارایی اضافه شده‌اند)
- محدودیت CHECK روی فرمت تلفن — دفاع در عمق در سطح DB
- تاریخچه مایگریشن تمیز و مرتب (۲۲ مایگریشن، بدون انشعاب)

**نقاط ضعف:**
- `TimeSlot.is_reserved` بدهی فنی است (اطلاعات `status` را تکرار می‌کند)
- `Vendor.average_rating` بدون تریگر DB غیرنرمال شده — به صحت کد اپلیکیشن متکی است
- `sport_types` ARRAY(String) فاقد ایندکس GIN برای کوئری‌های containment
- بدون soft-delete — حذف تصادفی بدون پشتیبان قابل بازیابی نیست

## کیفیت طراحی API

**امتیاز: قوی (۸/۱۰)**

RESTful، خوب مستند شده، با الگوهای مداوم.

**نقاط قوت:**
- نامگذاری مداوم REST (`/api/v1/vendors/{id}/slots`)
- صفحه‌بندی مبتنی بر cursor برای کارایی در مقیاس
- سیستم رده‌بندی احراز هویت واضح (public, optional, user, manager, admin)
- پاسخ‌های خطای ساختاریافته با ترجمه فارسی، شناسه درخواست و جزئیات سطح فیلد
- مستندات OpenAPI بهبودیافته با `openapi_docs.py`
- محدودیت نرخ در endpointهای حساس

**نقاط ضعف:**
- برخی endpointها اشکال پاسخ مختلف برمی‌گردانند (ناسازگار بین list/detail)
- مسیرهای قدیمی (`/courts/`) برای سازگاری معکوس هنوز سوار هستند (حجم سطح API)
- بدون استراتژی نسخه‌بندی API فراتر از پیشوند `/v1` (مسیر مهاجرت v2 واضح نیست)

## کیفیت فرانت‌اند

**امتیاز: خوب (۷/۱۰)**

برنامه Next.js با سازماندهی خوب با پشتیبانی خوب از فارسی/RTL.

**نقاط قوت:**
- استفاده مداوم از primitivesهای shadcn/ui — زبان طراحی منسجم
- RTL-اول با یکپارچه‌سازی DirectionProvider ریدکس
- تازه‌سازی توکن با deduplication تک-درحال-پرواز به خوبی پیاده‌سازی شده
- اسکیماهای Zod مشترک بین اعتبارسنجی فرم و نوع‌های API
- تبدیل ارقام فارسی به طور مداوم از طریق utility اعمال شده

**نقاط ضعف:**
- بیشتر صفحات رندر شده سمت کلاینت (`"use client"`) — مزایای SSR/RSC Next.js را از دست می‌دهد
- بدون کتابخانه state سراسری — می‌تواند به prop drilling در درخت کامپوننت عمیق منجر شود
- بدون تست E2E (فقط تست‌های واحد/کامپوننت)
- برخی فایل‌های صفحه بزرگ (جزئیات مجموعه >۱۰۰۰ خط) می‌توانند تجزیه شوند

## امنیت

**امتیاز: قوی (۸/۱۰)**

مدل امنیتی جامع با چندین لایه دفاعی.

**نقاط قوت:**
- JWT با چرخش کلید، نسخه‌بندی توکن، مدیریت نشست
- چرخش توکن refresh با تشخیص replay
- هش رمز عبور bcrypt با اعمال حداقل طول کلید
- محدودیت نرخ (پشتیبان Redis با fallback تدریجی)
- هدرهای امنیتی (HSTS، CSP، X-Frame-Options و غیره)
- اعتبارسنجی آپلود فایل (بایت‌های جادویی، نه فقط پسوند)
- محدودیت فرمت تلفن در سطح DB
- قفل OTP بعد از ۵ تلاش ناموفق
- لاگ حسابرسی برای تمام رویدادهای امنیتی

**نقاط ضعف:**
- توکن دسترسی در کوکی غیر httpOnly ذخیره می‌شود (XSS → سرقت توکن)
- CORS روی `*` در محیط توسعه (اعتبارسنجی شده اما فقط هشدار می‌دهد، راه‌اندازی را مسدود نمی‌کند)
- بدون محافظت CSRF (متکی به کوکی SameSite + توکن Bearer)
- بدون قفل حساب در تلاش‌های ناموفق رمز عبور (فقط OTP قفل دارد)

## کارایی

**امتیاز: خوب (۷/۱۰)**

**نقاط قوت:**
- صفحه‌بندی مبتنی بر cursor (O(log n) در مقابل O(n) برای offset)
- کش Redis با jitter (جلوگیری از stampede)
- پول اتصال با pre_ping
- زمان‌سنجی کوئری برای شناسایی کوئری‌های کند
- SELECT FOR UPDATE در ایجاد رزرو (جلوگیری از به‌روزرسانی‌های گمشده)

**نقاط ضعف:**
- TTL کش خیلی کوتاه است (۳۰ ثانیه برای سانس‌ها، ۶۰ ثانیه برای لیست‌های ادمین) — نرخ بالای cache miss
- بدون کش نتایج کوئری در سطح ORM
- وظایف پس‌زمینه در بازه‌های ثابت (۶۰/۱۲۰ ثانیه) رای‌گیری می‌کنند به جای رویداد-محور
- بدون بهینه‌سازی کوئری دیتابیس قابل مشاهده (بدون SQL خام، بدون مستندات query plan)
- ایندکس GIN گمشده برای کوئری‌های آرایه sport_types

## مقیاس‌پذیری

**امتیاز: متوسط (۶/۱۰)**

طراحی شده برای مقیاس تک‌شهر (قم) — مناسب برای نیازهای فعلی.

**نقاط قوت:**
- بک‌اند بدون حالت (مقیاس‌دهی افقی ممکن)
- Redis برای حالت اشتراکی (نشست‌ها، محدودیت نرخ، کش)
- اندازه پول اتصال مناسب برای همزمانی متوسط
- ایندکس partial unique از دوبل‌بوکینگ بدون قفل اپلیکیشن جلوگیری می‌کند

**محدودیت‌ها:**
- نمونه PostgreSQL تکی (بدون read replica، sharding یا پارتیشن‌بندی)
- وظایف پس‌زمینه درون‌فرآیندی (بدون صف وظیفه خارجی مثل Celery)
- آپلود فایل‌ها به صورت محلی (`uploads/`) ذخیره می‌شوند — نه CDN/S3
- بدون WebSocket/SSE برای به‌روزرسانی بلادرنگ (مبتنی بر polling)
- فرض استقرار تک-منطقه

## قابلیت نگهداری

**امتیاز: قوی (۸/۱۰)**

**نقاط قوت:**
- ساختار پوشه واضح با نامگذاری مداوم
- مایگریشن‌های Alembic به درستی زنجیره شده (بدون یتیم)
- هوک‌های Lefthook قالب‌بندی را قبل از commit اعمال می‌کنند (Ruff، Prettier، ESLint)
- Makefile با اهداف جامع
- type hint در سراسر کد Python
- Conventional Commits اعمال می‌شود
- ۲۴۸ تست عبور می‌کنند (پوشش خوب مسیرهای خوشحال و موارد لبه)

**نقاط ضعف:**
- دو کامیت یکپارچه بزرگ در تاریخ اخیر (بسته‌بندی چندین ویژگی)
- مقداری تکرار کد در ساخت پاسخ رزرو
- docstring گمشده در چندین متد سرویس

## اولویت‌های بهبود آینده

۱. **یکپارچه‌سازی درگاه پرداخت واقعی** — جایگزینی mock با الگوی آداپتر پشتیبانی از زرین‌پال/ملت
۲. **ارائه‌دهنده SMS واقعی** — جایگزینی mock با کاوه‌نگار/فراز اس ام اس
۳. **ذخیره‌سازی آبجکت** — انتقال آپلودها به فضای ذخیره‌سازی سازگار با S3 (MinIO/Arvan)
۴. **تست E2E** — افزودن تست Playwright برای جریان رزرو، پرداخت، لغو
۵. **سفت‌کردن توکن دسترسی** — انتقال به کوکی httpOnly یا پیاده‌سازی الگوی BFF
۶. **صف وظیفه** — استخراج وظایف پس‌زمینه به Celery/ARQ برای قابلیت اطمینان
۷. **Read Replica** — وقتی بار کوئری افزایش یافت، افزودن read replica PostgreSQL
۸. **اعلان‌های WebSocket** — تأیید بلادرنگ رزرو و به‌روزرسانی سانس
۹. **ایندکس GIN روی sport_types** — بهینه‌سازی کوئری‌های فیلتر مجموعه
۱۰. **تجزیه سرویس** — تقسیم booking_service.py به booking_creation، booking_payment، booking_cancellation
