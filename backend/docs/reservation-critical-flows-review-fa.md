# بررسی جامع منطق رزرواسیون توپ‌ست

> **وضعیت سند:** این سند در آغاز بررسی برای ثبت خط مبنا نوشته شد. نقص‌های قطعی مطرح‌شده
> در آن، به‌جز اتصال provider واقعی پرداخت و reconciliation بیرونی، اصلاح شده‌اند.
> نتیجه نهایی، state machine اجراشده و شواهد تست در
> [`full-project-business-logic-review-fa.md`](./full-project-business-logic-review-fa.md)
> آمده است. عبارت‌های «نقص» در ادامه، رفتار پیش از اصلاح را توضیح می‌دهند.

## هدف این سند

رزرواسیون مهم‌ترین بخش سامانه است. اگر دو نفر بتوانند یک سانس را بگیرند، یا پول کاربر
دریافت شود ولی رزرو قطعی نشود، اعتماد به کل سامانه از بین می‌رود. این سند رفتار فعلی
را ساده و مرحله‌به‌مرحله توضیح می‌دهد، تست‌های حیاتی را معرفی می‌کند و مشخص می‌کند
کدام قسمت‌ها مناسب‌اند و کدام قسمت‌ها قبل از production باید اصلاح شوند.

سرویس‌های بیرونی مثل درگاه واقعی پرداخت، پیامک و بانک عمداً موضوع این ارزیابی نیستند.
تمرکز سند روی قواعد دامنه، transaction دیتابیس، وضعیت رزرو و آثار مالی ثبت‌شده در
سیستم است.

فایل تست اصلی این بررسی:

- `tests/test_reservation_critical_flows.py`

## قانون طلایی رزرواسیون

در هر لحظه یک سانس فقط می‌تواند یک رزرو فعال داشته باشد؛ فرقی ندارد درخواست‌کننده:

- کاربر عادی باشد؛
- سالندار رزرو دستی ثبت کند؛
- ادمین از مسیر مدیریتی اقدام کند؛
- یا رزرو جدید قرار باشد جایگزین رزرو در حال لغو شود.

منظور از رزرو فعال یکی از وضعیت‌های زیر است:

- `pending_payment`: کاربر در مهلت پرداخت است؛
- `confirmed`: رزرو قطعی شده است؛
- `pending_cancellation`: رزرو قبلی منتظر جایگزین است.

تنها استثنا، فرایند جایگزینی است. در این فرایند برای مدت کوتاهی دو رکورد وجود دارد،
ولی آن‌ها دو مالک مستقل نیستند: رزرو جدید با `replaces_booking_id` به رزرو قبلی متصل
است و باید مثل یک انتقال کنترل‌شده مدیریت شود.

## چرا فقط بررسی `is_reserved` کافی نیست؟

بررسی برنامه کافی نیست، چون دو درخواست می‌توانند تقریباً هم‌زمان مقدار آزاد را بخوانند.
راه امن سه لایه دارد:

1. خواندن slot با `SELECT ... FOR UPDATE`؛
2. بررسی دوباره وضعیت داخل همان transaction؛
3. constraint دیتابیس به‌عنوان آخرین خط دفاع.

تست‌های concurrency جدید از connection و transaction مستقل استفاده می‌کنند. بنابراین
واقعاً دو درخواست هم‌زمان اجرا می‌شوند و صرفاً دو درخواست پشت‌سرهم نیستند.

### رقابت user با user

انتظار:

- دقیقاً یکی رزرو `pending_payment` می‌سازد؛
- درخواست دیگر پاسخ کنترل‌شده `409 Conflict` می‌گیرد؛
- فقط یک رزرو فعال در دیتابیس باقی می‌ماند؛
- هیچ `IntegrityError` نباید به 500 تبدیل شود.

### رقابت user با سالندار

رزرو آنلاین و رزرو دستی باید از یک قفل و invariant مشترک استفاده کنند. نقش سالندار
نباید باعث دورزدن رزرو در حال پرداخت کاربر شود. نتیجه باز هم باید دقیقاً یک موفقیت و
یک `409` باشد.

### رقابت user با ادمین

ادمین مجوز بیشتری برای مشاهده و مدیریت دارد، اما مجاز نیست قاعده انحصاری بودن سانس را
نقض کند. دسترسی بالاتر نباید به معنی bypass کردن consistency دیتابیس باشد.

## چرخه رزرو عادی کاربر

### ایجاد رزرو

رفتار درست فعلی:

1. vendor باید فعال باشد؛
2. زمان سانس نباید گذشته باشد؛
3. سانس باید در بازه عمومی ۱۴ روزه باشد؛
4. ظرفیت بررسی می‌شود؛
5. قیمت سانس و توپ همان لحظه در booking کپی می‌شود؛
6. booking به `pending_payment` می‌رود؛
7. slot به `reserving` می‌رود؛
8. مهلت پرداخت ده دقیقه ثبت می‌شود.

کپی‌کردن قیمت تصمیم درستی است. اگر سالندار بعداً قیمت سانس یا توپ را تغییر دهد، مبلغ
رزرو قبلی نباید عوض شود.

### پرداخت موفق

پس از موفقیت:

- payment موفق ثبت می‌شود؛
- booking به `confirmed` می‌رود؛
- slot به `reserved` می‌رود؛
- مبلغ booking مبنای گزارش مالی و تسویه قرار می‌گیرد.

تلاش دوباره برای پرداخت booking قطعی‌شده باید رد شود تا ثبت مالی تکراری ایجاد نشود.

### پایان مهلت پرداخت

انتظار مطلوب:

- booking به `expired` برود؛
- slot فقط زمانی آزاد شود که هنوز متعلق به همان booking باشد؛
- عملیات با قفل و شرط اتمیک انجام شود؛
- اجرای هم‌زمان چند worker نتیجه را خراب نکند.

این نقص اصلاح شد: job با `FOR UPDATE SKIP LOCKED` کار را بین workerها تقسیم می‌کند،
مالکیت مؤثر slot را پیش از آزادسازی می‌سنجد و endpoint پرداخت نتیجه `expired` را پیش از
برگرداندن خطای تجاری commit می‌کند.

پیشنهاد production این است که expiration با یک query شرطی یا `FOR UPDATE SKIP LOCKED`
انجام شود و شرط زیر را اتمیک بررسی کند:

```text
booking.status == pending_payment
booking.expires_at < now
slot.status == reserving
active booking of slot == this booking
```

## لغو رزرو پرداخت‌نشده

این ساده‌ترین لغو است:

- پولی دریافت نشده؛
- booking به `cancelled` می‌رود؛
- slot دوباره `open` می‌شود؛
- refund و penalty نباید ساخته شوند؛
- کارت بانکی لازم نیست.

برای این مسیر تست مستقل نوشته شده است و علاوه بر پاسخ API، وضعیت slot و تعداد refundها
را مستقیماً در دیتابیس بررسی می‌کند.

## لغو رزرو قطعی بیشتر از ۴۸ ساعت قبل

قاعده فعلی محصول:

- کاربر باید شروط را تأیید کند؛
- کارت بانکی تأییدشده لازم است؛
- جریمه ۱۰ درصد است؛
- refund برابر ۹۰ درصد مبلغ snapshot شده booking است؛
- booking به `cancelled` می‌رود؛
- settlement status به `excluded_due_to_refund` می‌رود؛
- slot آزاد می‌شود؛
- یک penalty و یک refund ساخته می‌شود.

از نظر حسابداری ساختار کلی درست است، چون مبلغ اصلی، قیمت توپ، جریمه و مبلغ عودت در
refund snapshot می‌شوند. بهتر است تمام محاسبات فقط با `Decimal` انجام شوند؛ استفاده
موقت از `float` برای پول می‌تواند در مبالغ اعشاری خطای rounding بسازد.

## لغو رزرو قطعی در ۴۸ ساعت پایانی

در این حالت پول فوراً عودت داده نمی‌شود:

- booking به `pending_cancellation` می‌رود؛
- slot هم `pending_cancellation` و همچنان reserved می‌ماند؛
- کاربر قبلی تا پیدا شدن جایگزین مالک رزرو محسوب می‌شود؛
- refund و penalty هنوز ساخته نمی‌شوند.

اگر جایگزین پیدا نشود، job انقضا درخواست/hold را می‌بندد، slot را به رزرو اصلی برمی‌گرداند
و رزرو قدیمی را مطابق state machine حفظ/قطعی می‌کند؛ بنابراین وضعیت میانی بدون صاحب
رها نمی‌شود.

## فرایند جایگزینی

چرخه مطلوب:

```text
رزرو قبلی: confirmed
    ↓ درخواست لغو در ۴۸ ساعت پایانی
رزرو قبلی: pending_cancellation
slot: pending_cancellation
    ↓ کاربر دوم رزرو می‌کند
رزرو جدید: pending_payment + replaces_booking_id
slot: reserving
    ↓ پرداخت کاربر دوم
رزرو جدید: confirmed
رزرو قبلی: transferred
slot: reserved
refund قبلی: 90%
penalty قبلی: 10%
```

### نقص اول در خط مبنا: constraint رزرو فعال

partial unique index وضعیت `pending_cancellation` و `pending_payment` را هم‌زمان active
می‌داند و اجازه ایجاد رکورد جایگزین را نمی‌دهد. بنابراین مدل دیتابیس با نیاز جایگزینی
تضاد دارد.

راه‌حل مناسب یکی از این دو طراحی است:

1. نگهداری hold جایگزین در جدول جداگانه و تبدیل آن به booking پس از پرداخت؛
2. اصلاح constraint به شکلی که فقط یک booking اصلی و حداکثر یک replacement مرتبط
   مجاز باشد.

گزینه اول پیاده شد: `ReplacementRequest` و `BookingHold` در جدول‌های جدا نگهداری می‌شوند
و فقط پس از پرداخت موفق، booking جدید در همان transaction ساخته می‌شود.

### نقص دوم در خط مبنا: تضاد وضعیت slot

این تضاد با state machine hold اصلاح شد. slot در زمان hold تحت قفل به `reserving` می‌رود
و در پرداخت، شکست، لغو یا انقضا فقط از transitionهای تعریف‌شده به وضعیت مناسب بازمی‌گردد.

### شکست پرداخت جایگزین

اگر پرداخت replacement شکست بخورد، رزرو قبلی نباید تغییر کند. اگر مهلت replacement
تمام شود:

- replacement باید `expired` شود؛
- رزرو قبلی باید `pending_cancellation` بماند؛
- slot باید به `pending_cancellation` برگردد؛
- refund نباید ساخته شود.

### موفقیت پرداخت جایگزین

تمام عملیات زیر باید در یک transaction انجام شوند:

- ثبت موفق payment جدید؛
- confirmed شدن رزرو جدید؛
- transferred شدن رزرو قبلی؛
- ساخت یک refund برای رزرو قبلی؛
- ساخت یک penalty؛
- reserved شدن slot.

اگر هر مرحله شکست خورد، هیچ‌کدام نباید commit شود. unique constraint روی
`(booking_id, refund_type)` برای جلوگیری از refund تکراری تصمیم خوبی است.

تست این چرخه اکنون تست عادی و سبز است و موفقیت، شکست، expiry، retry و یکتایی refund را
بررسی می‌کند؛ `xfail` بحرانی باقی نمانده است.

## لغو توسط سالندار

### رزرو آنلاین و پرداخت‌شده

انتظار:

- booking لغو شود؛
- refund صددرصدی ساخته شود؛
- جریمه کاربر صفر باشد؛
- `site_bears_penalty=true` ثبت شود؛
- booking از تسویه سالندار خارج شود؛
- slot بسته به انتخاب مدیر آزاد یا blocked شود.

این مدل مالی منطقی است: کاربر نباید هزینه تصمیم سالندار را بپردازد.

### رزرو دستی

چون در سیستم پول آنلاین دریافت نشده است:

- booking لغو می‌شود؛
- refund بانکی ساخته نمی‌شود؛
- settlement status از ابتدا خارج از تسویه آنلاین است؛
- slot آزاد یا blocked می‌شود.

### نکته دسترسی

سالندار فقط باید رزرو vendor خودش را لغو کند. ادمین می‌تواند نقش نظارتی داشته باشد، ولی
تمام عملیات او نیز باید audit شود. نقش بالاتر نباید constraint انحصاری slot را دور بزند.

### نقص پاسخ endpoint رزرو دستی در خط مبنا

تست API نشان داد پس از ساخت رزرو دستی، serializer به رابطه `booking.slot` دسترسی lazy دارد
و در SQLAlchemy async با `MissingGreenlet` مواجه می‌شود. خود رزرو در service ساخته می‌شود،
اما endpoint می‌تواند به‌جای پاسخ ۲۰۱ خطای ۵۰۰ بدهد و transaction نیز rollback شود. پیش از
serialization باید booking با `slot` و `vendor` به‌صورت eager دوباره خوانده شود یا response
مستقیماً از داده‌های از قبل موجود ساخته شود.

هر دو مسیر با eager-load/response construction ایمن اصلاح شده‌اند و تست API آن‌ها بدون
`xfail` اجرا می‌شود.

## رزرو تکرارشونده مدیر

رفتار `allow_partial=false` باید all-or-nothing باشد: وجود یک conflict یعنی هیچ رزروی
ساخته نشود. در `allow_partial=true` فقط slotهای آزاد ساخته می‌شوند و conflictها همراه
پاسخ برمی‌گردند.

اعتبارسنجی اکنون موارد زیر را enforce می‌کند:

- روز هفته فقط ۰ تا ۶؛
- زمان واقعی و معتبر، نه فقط قالب دو رقم؛
- پایان بعد از شروع؛
- حذف روزهای تکراری؛
- جلوگیری یا تصمیم صریح درباره تاریخ گذشته؛
- سقف تعداد رزرو تولیدشده، نه فقط سقف ۶ ماه.

## ثبت پرداخت ناموفق

نتیجه payment ناموفق اکنون پیش از برگرداندن خطای تجاری commit می‌شود؛ notification و
audit مرتبط نیز از بین نمی‌روند. برای provider واقعی همچنان جدول intent/callback و
reconciliation توصیه می‌شود.

در production بهتر است payment attempt چرخه transaction مستقل داشته باشد یا نتیجه
درگاه ابتدا در یک جدول append-only ثبت شود. شکست تجاری پرداخت نباید با شکست transaction
دیتابیس یکی تلقی شود.

## ارزیابی نهایی

### نقاط خوب

- استفاده از row lock در مسیرهای اصلی؛
- version افزایشی برای اطلاع UI و row/advisory lock برای جلوگیری از race؛
- snapshot قیمت در booking و refund؛
- تفکیک source رزرو آنلاین و دستی؛
- مدل settlement و refund نسبتاً شفاف؛
- constraint جلوگیری از refund تکراری؛
- کنترل مالکیت vendor در عملیات مدیر.

### موارد باقی‌مانده قبل از production

1. اتصال gateway واقعی و callback امضاشده؛
2. idempotency key مورد توافق PSP و reconciliation برای وضعیت نامطمئن؛
3. اجرای مداوم تست concurrency روی PostgreSQL واقعی در CI؛
4. metric/alert و repair console برای payment/holdهای قدیمی؛
5. تصمیم و پیاده‌سازی سیاست rounding مشترک با سرویس مالی بیرونی.

## state machine پیشنهادی

بهتر است transitionها در یک محل مرکزی تعریف شوند، نه با شرط‌های پراکنده:

```text
pending_payment -> confirmed | cancelled | expired
confirmed -> cancelled | pending_cancellation
pending_cancellation -> transferred | confirmed_after_no_replacement
```

و برای slot:

```text
open -> reserving -> reserved
reserved -> open | blocked | pending_cancellation
pending_cancellation -> reserving -> reserved
reserving -> open | pending_cancellation | reserved
```

هر transition باید سه چیز داشته باشد:

- precondition واضح؛
- تغییر اتمیک booking و slot؛
- تست success، failure و concurrency.

## معیار پذیرش نهایی

بخش رزرواسیون زمانی آماده production است که:

- تمام تست‌های عادی سبز باشند؛
- هیچ `xfail` بحرانی باقی نماند؛
- سه تست concurrency چند بار متوالی پایدار اجرا شوند؛
- هیچ conflict قابل انتظار به 500 تبدیل نشود؛
- مجموع مالی همیشه برقرار باشد:

```text
total_paid = refund_amount + penalty_amount
```

- برای هر slot حداکثر یک مالک مؤثر وجود داشته باشد؛
- retry درخواست‌ها payment، refund یا booking تکراری نسازد.
